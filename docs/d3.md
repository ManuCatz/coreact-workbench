# d3 Dependency — Analysis Summary

## 1. Question

Should coreact2 keep its d3 dependency, and what would dropping it entail?

## 2. Current d3 usage (inventory)

The actual d3 surface used across the codebase is small — essentially the
`selection` subset plus `pointer`.

- **`src/default_sorts.ts`**: only `import('d3')` type annotations plus the
  d3-Selection `context` API (`append`, `attr`, `text`, `insert`, `select`,
  `empty`). No direct runtime `d3.*` use. The compiled `public/default_sorts.js`
  has no d3 reference at all — the dependency is *indirect*, through the
  `context` argument passed into each draw function.
- **`src/index.ts`**: ~7 lines in `Drawing.draw()` (index.ts:892-917) —
  `context.append`, `.attr`, `.classed`, `.selectAll`. No d3 import; `context`
  is typed `any`.
- **`src/main.ts`**: ~18 lines — `d3.select("#canvas")`, `d3.pointer`,
  `svgContext.on("click")`, `selectAll("*").remove()` (x3), cursor styling
  (`d3.select("body").style(...)`, x4), and 7 `svgElement.attr("opacity", ...)`
  sites.
- d3 is injected as a global into user-authored sort scripts via
  `new Function('sortStore', 'd3', code)` (main.ts:10, main.ts:2044), so custom
  sorts can reach for `d3.*` — a public authoring surface.
- **`puppeteer`** sits in runtime `dependencies` but is not imported anywhere in
  `src/` — it is a dev-time tool.

## 3. Option A: d3-lite `context` shim

- Keep the d3-shaped authoring API so `default_sorts` bodies and user sort
  scripts survive nearly unchanged.
- ~150-line wrapper implementing `append/attr/text/select/insert/empty/classed`
  over native DOM.
- Zero dependencies; confines changes to one new file + type annotations.

## 4. Option B: native DOM

- ~25 lines of changes in `index.ts`/`main.ts`, mostly mechanical swaps.
- The one non-trivial piece: replacing `d3.pointer` (main.ts:130) with
  `createSVGPoint()` + `matrixTransform(getScreenCTM().inverse())`.
- `default_sorts` stays roughly the same length but becomes more verbose per
  element (extra `createElementNS` + `appendChild`); `svgElement` becomes a
  native `SVGElement`, so every `.attr(...)` on it (8 sites) becomes
  `.setAttribute(...)`.
- Call-site table:

  | index.ts | d3 usage | native replacement |
  |---|---|---|
  | 892-894 | `context.append("g").attr(...)` | `createElementNS` + `setAttribute` + `appendChild` |
  | 897 | `layerGroup.attr("display","none")` | `setAttribute("display","none")` |
  | 907-908 | `svgElement.attr("opacity",...)` guard | element truthiness + `.setAttribute` |
  | 915-917 | `.classed(...)` + `selectAll(...).attr(...)` | `classList`/`setAttribute` + `querySelectorAll(...)` |

  | main.ts | d3 usage | native replacement |
  |---|---|---|
  | 1, 10 | `import * as d3`; `new Function(...,'d3',...)` | removed |
  | 75 | `d3.select("#canvas")` | `document.querySelector("#canvas")` |
  | 127 | `svgContext.on("click", ...)` | `addEventListener` |
  | 130 | `d3.pointer(event, node)` | `getScreenCTM().inverse()` math |
  | 146, 729, 2687 | `selectAll("*").remove()` | `replaceChildren()` |
  | 124, 1404, 2518, 2844 | `d3.select("body").style("cursor",...)` | `document.body.style.cursor` |
  | 766, 781, 1023, 1040, 1058, 1761, 1769 | `svgElement.attr("opacity",...)` | `.setAttribute("opacity",...)` |

## 5. Worth it?

- Only if bundle size is a measured problem. The d3 modules used are the
  lightweight ones (`selection`, `pointer`) — none of the heavy ones
  (`d3-scale`, `d3-force`, `d3-shape`, `d3-zoom`) are used. Savings would be
  roughly d3's core (~30-40KB min+gzip).
- The `context` API is the **public authoring contract** for user sort scripts —
  that is the real cost of dropping d3, not the ~25 lines.
- A bigger, cheaper win regardless: move `puppeteer` to `devDependencies`.

## 6. Alternatives

- **SVG.js** (`@svgdotjs/svg.js`): MIT, zero dependencies, ~65KB min, actively
  maintained (v3.2.x). SVG-only, chainable API matching the imperative
  `append/attr` style used here. `element.point(x, y)` covers `d3.pointer`
  (returns `{x,y}` instead of `[x,y]`; takes raw coords, not event + node).
  Different API, so `default_sorts` bodies and the `context` contract still get
  rewritten. Recommended over d3 **if implementing from scratch** for this
  codebase, assuming no d3-scale/zoom/transition features are planned.
- **Native DOM**: smallest and zero-dep, but verbose authoring for user scripts.
- **Own d3-lite shim**: keeps authoring API, zero-dep, minimal churn.
- **Non-candidates**: snap.svg (unmaintained since ~2018), Raphaël (ancient),
  Fabric.js/Konva (canvas paradigm, wrong fit for `createElementNS`-style SVG).

## 7. Why enter/update/exit isn't used

d3's join model (`.data(arr, key).join(...)`) is for *data-driven incremental
reconciliation*; coreact2's architecture has none of its prerequisites:

1. **Imperative + bespoke drawing callbacks.** Sort functions hand-build
   arbitrary geometry (Bézier control points, arrowheads, offset polylines) with
   `append/attr` (default_sorts.ts) and return the element. Joins only manage
   the top-level selection per container and cannot diff those nested scenes.
2. **Full redraw model.** Every mutation flows through `updateCanvas` →
   `svgContext.selectAll("*").remove()` → `drawing.draw()` (main.ts:729-731).
   Scenes are small and redraw is cheap, so there is nothing to avoid.
3. **The few partial updates use the opposite pattern.** Hover/focus/merge
   opacity is applied to *stored element references* (`artefact.svgElement.attr`,
   index.ts:907, main.ts:766-781) — a stateful scene-graph approach that a
   stateless data-join architecture would break.

Conclusion: d3 is used correctly here — as an SVG manipulation library. Even
that exceeds the surface, which is what keeps the shim option attractive.
Not using joins is a feature of the design, not a missed opportunity.



# My own conclusion

partial updates should be dealt in anotherway so we can use d3's join model when 
drawing performance becomes ever an issue
